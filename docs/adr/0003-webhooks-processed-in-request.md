# Webhooks are processed in the request, in one transaction

Pixelforge's docs suggest responding quickly and doing slow work in a queued job. We deliberately process each webhook inside the HTTP request, in a single database transaction: verify the signature, record the event id (unique, so a duplicate is a no-op), lock the generation, apply the status change only if it moves forward, and record the actual charge on the move to succeeded. The work takes milliseconds, well under the 10-second limit. Doing it atomically means two copies of the same event arriving at once can't both slip through, and there's no second place for an event to get lost between receipt and processing. Queued jobs remain for genuinely slow work: submitting generations to Pixelforge and retrying them.
